## C2: "screen changed outside the app" check

For the changelog: after a check, if the screen's free space is clearly different from what it was when CoolerScreen last stored
something, a warning banner says "The screen changed since CoolerScreen last stored Embedded (free space X MB then, Y MB now).
Another program may have written to it." with an "It's fine" button (accepts the screen as it is now). Storing something again
(Store as Embedded / Apply) clears it.

How it works (read-only; nothing is sent to the screen, no 0x05, 0x0C or 0x23): the info answer every check already gets has
`i_block_free`. `screenBaseline {free, at}` in settings.json is set from the final check of each store, or from the first check when
there is none yet (a fresh install or an upgrade cannot know the past). A later check with |free - baseline| > 64 blocks (32 KB)
writes `screenChanged {was, now, blockSize, at}`, logs "Screen changed outside the app: ..." once in device.log, and `app_state`
returns `screenChanged {wasFree, nowFree, at}` (bytes). A store whose final check failed drops the baseline (no false alarm; the next
check starts over). Not run while live holds the screen (that path never queries the screen).
Code: `src/core/outside.rs`; hooks in service.rs (device_check, send_version, app_state, settings_update `screenChanged: "accept"`),
settings.rs sanitize (both keys written only when set), device_service.rs (fake `free` + `fake_set_free` test hook), app.js banner.
Test: `a_check_flags_screen_content_changed_outside_the_app` (fake device: first check, wobble inside tolerance, big change, repeat
keeps "was", accept, rebase after a store, failed final check). Full suite passes at default threads.

restart? if it wobbles by more than 64 blocks, raise TOLERANCE_BLOCKS in outside.rs); (2) the banner would only be seen after

## C4: `CoolerScreen.exe --quit` (4.9.1)

What it is: a clean way for the installer workflow to quit the running app (tools/README.md has the exit codes).
`--quit` is handled at the very top of `main()` (before Tauri or the single-instance plugin start), so it can return its own exit
code, never creates a window and never starts an app. Exit codes: 0 quit, 1 asked but still running after 20 s, 2 refused (a visible
job is queued or running: upload, conversion, store, recording; nothing done), 3 no running instance.

How: the running app owns a named event `Local\CoolerScreenQuit-<hash of its app folder>` (a thread blocked on it: no polling, nothing
runs until signalled). Because the name follows the app folder, an instance with another COOLERSCREEN_HOME (every test instance)
can never be reached by, or answer for, the installed app. `--quit` signals it and reads `quit.result` ("ok <pid>" or "busy") in
the app folder, then waits for that pid to end. The app then runs the existing `quit_app` (same as tray Quit: `live.stop()`
hand-back, exit watchdog 3 s). device.log gets "quit requested (--quit): the tray Quit path" or "...a job is running: refused".

**PM install recipe:**
1. `& CoolerScreen.exe --quit` (the installed exe, normal app folder); `$LASTEXITCODE`: 0 = quit, go on; 3 = not running, go on;
   2 = a job is running: wait and retry (do not force); 1 = still running after 20 s: look before forcing.
2. Run the installer silently (`/S`) and wait for it to end.
3. `CoolerScreen.exe --background` (quiet start).
(`Start-Process -Wait -PassThru` gives the code for a GUI-subsystem exe; plain `& exe` does not wait.)

Plain WM_CLOSE (taskkill without /F): not changed. With a window it already goes through the close handler (hides to the tray, or
destroys the window with Live on); with no window there is nothing to receive it, and `taskkill` reports it could not close the
process. That is why `--quit` exists; I did not add a hidden helper window just for it.

Verified with quiet DEBUG instances under a scratch COOLERSCREEN_HOME, fake device (script in my scratchpad `quittest.ps1`):
1. no instance: exit 3. 2. while a store job ran: exit 2, the app kept running and the job finished. 3. when idle: exit 0 after
1.0 s, the process was gone and device.log shows "quit requested (--quit): the tray Quit path" then "live: stop". 4. again: 3. The
user's installed app was not touched by `--quit` (different folder, different event).
Not verified: against a release build (by design, never against the user's), the 20 s "still running" path, a real USB stop.

**My mistake to know about:** my first test launch of a debug instance forgot `COOLERSCREEN_MULTI=1`, so the single-instance
plugin forwarded that launch to the user's running 4.9.0 (pid 7356) and its callback (`show_main`) probably brought its window up
once (around 14:17-14:18 local). I did not touch the app otherwise; the test instances now always set MULTI. Worth knowing for

## C5: "Store as Embedded" refused although "Preparing the picture" fitted (user bug, 4.9.1)

**Cause (found with the user's real files, see finding 4 for how I could read them):** two budgets disagreed.
Conversion, the Picture page and the Store pre-check used the *capacity budget* (settings.capacity, a record kept from the last
measurement, here 11,550,000 = the MAX_CAPACITY cap, minus splash 537,054 and SAFETY 160,000 = 10,852,946). The device guard
(`ops::loop_room`) used what the screen *reports now*: free blocks x 512 + the loop file it replaces (real record: standby 10,252,878
bytes, stored 2026-10-18 10:21 UTC) - 256,000 = 10.46 MB. The capacity record was optimistic by about 0.4 MB (it is clamped at
MAX_CAPACITY, while the screen's real numbers gave less), so a picture "that fits" could not be stored. Note the true numbers: the
free space is about 905 blocks, i.e. about what it was after the last store; there was no outside change (see finding 3).

**Fix:**
1. One loop budget: `settings::budgets()` = min(capacity budget, the screen's own loop room). The room is recorded
   (`loopRoom {bytes, at}` in settings.json) from every info answer: every check, the final check of a store, the skip-identical
   read, and a new refresh before each store. Everything that uses the budget (conversion `budget_bytes`, the "too big" mark, the
   Picture page meter, the send pre-check, the device guard) therefore agrees; the guard in `ops` still computes the same number from
   its own fresh info, so it can only agree or be stricter by the margin of a stale record.
2. `refresh_loop_room()` runs at the start of every Store as Embedded (`run_apply`): a read-only info (0x06) as a small hidden device
   task; with live on it steps live aside for a moment (a store pauses it for minutes anyway), because with live on nothing else ever
   reads the screen. Failures are ignored (last known budget stands; one line in device.log).
3. A finished version that no longer fits is not reused: `create_version`'s duplicate check ignores a ready version bigger than the
   current budget, so Store re-makes the picture "best that fits" instead of reusing the 10.83 MB one (test shows it: the old
   picture is replaced by a smaller one and the store succeeds). The page shows the old one as "too big" already.
4. The Picture page meter says "(all the free space your screen reports)" when the screen's room is the limit.
Margins, documented at `settings::SAFETY`: SAFETY (160 KB) = slack on the derived capacity number; `ops::LOOP_MARGIN` (256 KB) = the
screen's own bookkeeping kept free inside the real room. The true ceiling (measured 10,908,539) is not raised: the new rule only
ever lowers the budget.
Tests: `the_loop_budget_follows_the_screens_real_room` (budget == what the guard allows; recovers when space returns; failed final
check drops the record) and `storing_makes_the_picture_fit_the_screens_real_room` (the second store, with no check in between,
re-makes a smaller picture and succeeds). Suite: 274 pass.

**Finding 3 (why the C2 check did not flag it):** it could not have, for three reasons, and the premise was also off:
(a) the user's real settings.json has no `screenBaseline` at all: the last store (2026-10-18 10:21Z) predates C2, and the baseline is
only taken from an info answer; (b) with Live on at start the page's check is answered from the live session ("the last answer
stands", no info), so no check ever read the real free space, and the store path did not run one either; (c) C2 compares with the
baseline from our last store, so it needs (a). Fixed by the pre-store refresh above (it calls the same `note_screen_info`, so a
baseline is taken and any change > 64 blocks is flagged by the existing banner). (d) The premise: the ~690-block drop came from a
stale read of the slot record (standby 10,610,433 / "Evangelion v2"): the real record is 10,252,878 and the real room equals
about 905 free blocks, so the screen did NOT lose space after the last store; nothing needed flagging.

**Finding 4 (device.log "silent" since 14:38): not a logging bug; a stale view.** The real `%APPDATA%\CoolerScreen\device.log` has the
line "CoolerScreen 4.9.1 build 5205207 started, pid 23272" at 2026-10-19 03:38:46Z and keeps logging (it was written up to 05:01Z when
I looked, 56,842 bytes). What the PM and I saw was a frozen copy (224,150 bytes, last write 14:36:17 local, no NULs) because the
Claude desktop app is an MSIX-packaged app: processes it starts (our shells, scripts, test instances, `--quit`) see a private,
copy-on-write view of `%APPDATA%` (`C:\Users\pc\AppData\Local\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\CoolerScreen\...`);
once a packaged process has touched a file, later changes by the real app are invisible to it. The same stale view explains the wrong
slot record in the report. Read the real files from outside the package, e.g.
`Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{CommandLine='cmd /c copy /y C:\Users\pc\AppData\Roaming\CoolerScreen\device.log <somewhere>'}`
(WMI starts the process outside the package), then read the copy. Consequences worth acting on: nothing in the real app was wrong;
PM/worker diagnostics that read the app folder from a packaged shell can be stale; and my first `--quit` used a result *file* in the app
folder, which a packaged `--quit` would never see, so I changed `--quit` to answer through named kernel events only (no file); its four
exit codes were re-verified (3, 2, 0, 3) after the change. Installs/test instances that WRITE to %APPDATA% from a packaged shell also
write only into the private copy.

Also in this commit: two flaky child-process tests (`jobobject::children_die_with_the_app`, `media::sys::adopted_children_die_with_the_app`)
now wait up to 10 s for the system to end the child instead of a fixed 300/500 ms (they failed once in a full parallel run).

## E3: digital twin + smooth dragging (editor refinement round)

**Twin (backend):** `live/twin.rs` keeps the newest sent JPEG (the portrait 756x1680 frame the screen gets, so it already has the
screen fit, notch and rounded corners: "as on the screen") in memory, at most one per 60 ms (about 15 per second), and only while
the page has asked within the last 3 s (`wanted()`); the send thread copies a frame only then, so the cost is zero when the editor
is closed, hidden or minimised. The media server serves it at `<base>/twin/frame.jpg?since=<seq>` (204 when nothing is newer,
`X-Twin-Seq` header, no-store). New command `twin_watch {on}`: Live on = the frames the engine sends are copied (no second render);
Live off = a stream for the editor only (null sink: nothing is sent to the screen; render rate locked at 15, settings changes keep it;
never idle-held); it ends when the editor leaves/hides (`on:false`), or by itself 10 s after the page stopped asking; switching Live
on while it runs replaces it by live's real stream; quit/stop clears it. `status.twinning` tells the page.
**Cost (release build, standard theme, Live off, measured with `twin_cost`, `--ignored`):** 11 frames/s actually encoded (unchanged
pictures are skipped, as for the screen), render 4.3 ms + JPEG 8.5 ms per frame, **17% of one core = about 1.1% of this 16-core PC**
while the editor is open and looking; 0 otherwise. With Live on it adds only a copy of a ~100 KB JPEG per frame (no extra render or
encode). Not reduced further (a lower JPEG quality for the twin would save about a fifth); easy to do if wanted.
Limits: with Live on and the screen not connected (no device, or paused by a device task) no frames are sent, so the twin keeps its
last picture and then falls back to the still preview after 1.5 s; with the live layer off (live idle) the same fallback applies.
**Twin (page):** `public/js/twin.js` (new): a canvas under the boxes/guides/corners; turns the portrait frame back to landscape while
drawing; polls every 45 ms only while the stage is visible (`document.hidden` and a detached stage stop it and tell the engine);
`.stage.twin-on > img.layer {visibility:hidden}` hides the still images while frames are fresh. Hooks in `themes.js`: one import and
one line after the stage is built. Effects drawn by the still preview's own animation loop are left as they were (not removed, so
no E1 conflict; the twin simply covers them while live).
**Smooth dragging (`themes.js startDrag`, 3 small changes):** pointer events are folded into one placement per animation frame
(rAF); snap lines are rebuilt only when they change; the theme is sent to the engine every 120 ms while dragging (the live picture
and the twin catch up) and once more on release; and `appChanged()` no longer repaints (rebuilds) the boxes during a drag (the
library event the throttled saves cause would otherwise have dropped the drag).
**Verified:** unit tests (twin store, Live off stream renders for the editor at 15 and ends, Live on copies without a second stream);
quiet DEBUG fake-device instance driven by `tools/ui-shots/twin-flow.mjs` (needs `document.hidden` forced false: the quiet window
reports hidden): twin canvas shows the live picture (screenshot checked), frames flow, leaving On screen stops the editor-only

## C6: Restart button, `--restart`, `--update` (user request 2026-10-19)

What exists now:
- **Settings > top: "Restart CoolerScreen"** (troubleshooting). The app runs the tray Quit path (live hands back to Embedded) and a
  fresh copy starts, spawned by the app itself, window as usual (no `--background`). While a job runs it refuses with a message
  ("Something is still running ... Restart when it has finished."). Tauri command `app_restart`.
- **`CoolerScreen.exe --restart`**: like `--quit`; the app relaunches itself quietly (`--background`).
- **`CoolerScreen.exe --update <CoolerScreen_x.y.z_x64-setup.exe>`**: only when idle. The file name must be exactly that pattern, be an
  existing local file (no network path); the requester checks it (exit 4) and the app checks it again. The app quits cleanly, a
  detached helper waits for its exit (30 s limit: if the app does not exit, nothing is installed or started), runs the installer `/S`
  (10 min limit), then starts the new exe with `--background`. Whatever the installer did, the helper starts an app again.
- Exit codes (also in tools/README.md): 0 accepted and the app exited; 1 accepted, still running after 20 s; 2 busy (a job is
  running; nothing done); 3 no running instance (nothing started); 4 (`--update`) not an installer.
- `tools/install-when-idle.ps1` uses `--update` when the running exe contains the helper flag (`--relaunch-after`, checked as a
  literal in the exe, so no version guess), otherwise the old quit + `/S` without restart; 4.9.1 and older rules unchanged.

**Design (reuses C4's kernel-object protocol, no files):** the app owns events `Local\CoolerScreenQuit-<scope>` (quit),
`...-restart`, `...-update`; the requester creates answer events `-ok` / `-busy` / `-bad`, a named memory section `-arg` for the
installer path, and `-pid` into which the app writes its process id before answering "ok". The requester waits on that PROCESS, not on
the events (the new app uses the same event names within a second; waiting on the events made the first version return 1).
Scope = build kind + app folder, so a debug or scratch instance can never be reached by, nor answer for, the installed app.
The helper is this same exe in a special mode (`--relaunch-after <pid> <plain|background> <exe> [setup]`, handled before Tauri starts, so
no window and no single-instance forwarding). For an update the helper is a copy in %TEMP% (`CoolerScreen-updater-<pid>.exe`) because the
installer replaces the installed exe; copies of earlier runs are deleted at the next helper start (the running one cannot be, so
one copy stays until then). Spawned detached, no window, breaking away from the app's job object when allowed. Helper steps are logged
in device.log as "updater: ...".

**MSIX reasoning (checked):** a process inherits the package identity of the process that CREATES it (its parent), not of whatever
script asked for it. `--restart` / `--update` run in the shell only as requesters; the relaunch is created by the app itself, started
by the user from the Start menu or Explorer, which has no package identity, so the helper and the new app run outside the private
copy of %APPDATA% and write to the real folder. Test: a scratch instance started through WMI (Win32_Process.Create, outside any
package, as Explorer would) was restarted and updated from my shell; `GetPackageFullName` reported "no package" for the instance before and
after both (that includes my own shell in this session, which is not packaged here, so this run cannot show the difference; the
protection comes from the parent rule above, and the scripts of this repo must still be started by the app, never by a shell, when
the shell IS packaged). If the app itself was started from a packaged shell, its relaunch is packaged too (child of a packaged
process): not our case for the installed app.

**Verified (quiet debug instances, scratch HOME, debug builds have their own single-instance id; fake device):**
- `--update` with a non-installer file / a missing file: 4. No instance: `--quit`, `--restart`, `--update` all 3, nothing started.
- `--restart`: exit 0 after the old process ended; a new pid appeared with command line `... --background`; device.log: "restart
  (--restart) requested: the tray Quit path", "updater: started ... again (background)".

## Flaky `broken_clip_holds_then_times_out_to_the_gradient` (follow-up)

**Cause:** not the twin and not a bug in the pipeline's hold. The test starts the pipeline and then sets the broken-clip theme; the
pipeline thread is already rendering, so under load it can render and send a frame or more of the *default* theme before the new
theme arrives (the hold only applies once the broken clip is the background). My earlier fix measured "first send after the theme
change" and so counted such a frame as a break of the hold (first send at 0 ms < 1.5 s). The twin only copies frames the sender took
and cannot make the pipeline send earlier.
**Hardening (same claim, measured where it can be):** after the theme change the test lets 1 s pass and takes the `sent` count as
settled, then requires that it did not change until the first *gradient* frame appears (a frame drawn on the placeholder because
the wait is over), that this first gradient frame came after at least 2 s (the wait is 3 s), and that frames are sent again after it.
Not weakened: a pipeline that sent during the hold would still fail (sent would move before the first gradient frame). 16 of 16
full-suite runs with two copies running at once passed; the version before this change failed 14 of 16 runs once I had first tightened it
the wrong way (my first draft broke on the gradient frame before it was sent; fixed by waiting for the send).

## Ghost copies of a moved item (user bug on 4.15.0)

**Cause (in the engine, so the frames themselves were wrong, not only the editor's display):** with a screen fit set (the user has
one), the engine keeps two persistent layers: the widget layer and the fitted layer. A cluster of widgets clears only its own
rectangle when it is redrawn; the fitted resample reads a pixel or two BEYOND that rectangle, and the merged fitted rectangles that are
composited can be larger than any one cluster's region. What lay there was whatever an item had left at an earlier place, so every
move deposited stale translucent pixels that were blended into the picture again (stacked, offset edges and copies of cards and meter
bars; the effect grows with how often the theme is re-sent while dragging, which E3's throttled live updates made frequent). Without a
fit the cluster rectangle is the composited one, so it never showed.
**Fix (render.rs):** a changed layout (`update_bbox` on every theme change, and `update_fit_rects` also for a fit change) starts from an
empty widget layer and an empty fitted layer; every cluster is redrawn right after (`set_theme` resets the layer key). Cost: a 5 MB
memset per theme change (a few per second while dragging), nothing per frame.
**Test:** `a_moved_item_leaves_no_ghosts`: an item (meters, cores, stats, network, clock: translucent cards and bars) is dragged across the
picture in 9 big steps, alone and next to a fixed neighbour (rectangles merge and split), with and without a fit; the frame after the
moves must equal the frame of a fresh renderer with only the final theme (0 differing pixels). Checked that it fails without the fix
(1,069 differing pixels for meters with the fit) and passes with it. Without a fit it passed before too.
**Real screen:** yes, it could have shown the ghosts: they were in the rendered frames (the picture that is JPEG-encoded and sent), for
any user with a screen fit (the user's top 4 / left 9) whenever a widget was moved or resized and the theme re-sent, in the editor
with Live on. The editor's twin showed the same frames.
**Quiet DEBUG instance (fit top 4 / left 9, Meters dragged with the pointer through the real page):** the twin shows one clean copy
under the box mid-drag and while held (screenshot checked); no page errors. I could not show the *before* picture in the app (the
check is on the fixed build), the unit test is the before/after evidence. Not verified: on the real screen, and the user's exact
scenario of 3 to 4 big offset copies: my pre-fix measurement shows edge pixels differing by up to about a quarter of the card colour,
so the visible copies the user saw may be larger than what the test reproduces; if ghosts remain on a build with this fix, a frame dump
(COOLERSCREEN_DUMP_FRAMES) of the moving item is the next step.
