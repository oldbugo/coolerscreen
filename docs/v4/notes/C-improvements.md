# Stream C notes (small improvements)

## C1 (branch claude/vibrant-proskuriakova-d382db)

For the changelog (user-facing):
- **FPS counter.** Settings > Live screen now says "Running: 59.8 of 60 frames per second sent" (refreshes every 2 s while the
  page is open). New switch "Show the frame rate on the screen" (off by default) draws "59.8 / 60 fps" on a dark chip near the
  top left of the visible picture. It costs one division per second plus a small chip draw; nothing runs when it is off.
  Setting key `live.fpsOverlay` (settings.json), `fps_overlay` in companion.json; status key `measuredFps`.
  The number is frames actually *sent*: when nothing on the picture changes the engine only re-sends a few frames per second
  (the safety net), so a still theme shows a low number. That is by design, not a fault.
- **GPU power dash fixed.** Cause: the NVML lookups for power and fan used a corrupted symbol name (an unterminated, garbled
  string), so GPU power and GPU fan could never be read. Now fixed; also NVML is retried every 30 s if it was missing at start,
  reloaded if it stops answering, and device.log says why anything is unavailable ("gpu: NVML ready (... power readable)",
  "gpu: not available: ...", "gpu: power read failed (nvml code N)"). Checked on this PC: "NVML ready (RTX 5070 Ti, power readable)".
- **Countdown and daylight saving.** The info widget's countdown now converts both times to UTC with the PC's Windows time-zone
  rules, so across a change it counts real time (Sydney: the night of the October change is an hour shorter). Unit test with the
  Sydney rules for both changes. Needs windows-sys feature Win32_System_Time (Cargo.toml).
- **Dirty "+" in the build hash.** The check already ignored gen/ (cbc4424) but `tauri build` still rewrote tracked files
  (LF vs CRLF, and new commands in the schemas). Now `src-tauri/gen/` and `src-tauri/permissions/autogenerated/` are untracked
  and git-ignored, so nothing can dirty the tree. Verified: builds from a tree without them (they are regenerated), `git status`
  clean after a build, device.log first line shows "build 78c3c17" without "+" for a clean commit.
- **Flaky engine tests.** Real causes, found by running the suite 16 times with two copies at once: fixed sleeps that assumed
  the machine keeps up (live_host layer/tune tests, the 60/30 fps ratio test, the broken-clip hold test, cpu.load needing a
  delta, the ffmpeg probe timeout bound, the scheduler cancel bound). They now wait for the state (up to 10 s) and the same
  assertions follow; the fps ratio is re-measured up to 4 times and must hold once. Result: 16 of 16 runs at default test
  threads with double load pass (220 tests). `--test-threads=4` no longer needed.

Verification: unit tests (new: overlay chip, DST countdown, nvml symbol names, gpu source); quiet fake-device instance
(COOLERSCREEN_FAKE_DEVICE=1, MULTI=1, TEST_QUIET=1, own HOME, own CARGO_TARGET_DIR) with the overlay on: frame dump shows the
chip "11.0 / 60 fps" at the top left of the landscape picture.
Not verified: the overlay and the readout on the real screen; GPU power with the widget on the real device (NVML itself
reports it readable here); countdown on a real DST night (unit-tested only).

Note: while testing I (by mistake) ran a taskkill by image name; the user's app was not running (its device.log ends at the
forced shutdown, 2026-10-18 11:51 UTC), so nothing of the user's was closed. Test instances are now stopped by path filter.

## C2: "screen changed outside the app" check

For the changelog: after a check, if the screen's free space is clearly different from what it was when CoolerScreen last stored
something, a warning banner says "The screen changed since CoolerScreen last stored Embedded (free space X MB then, Y MB now).
Another program may have written to it." with an "It's fine" button (accepts the screen as it is now). Storing something again
(Store as Embedded / Apply) clears it.

How it works (read-only; nothing is sent to the screen, no 0x05, 0x0C or 0x23): the info answer every check already gets has
`i_block_free`. `screenBaseline {free, at}` in settings.json is set from the final check of each store, or from the first check when
there is none yet (a fresh install or an upgrade cannot know the past). A later check with |free - baseline| > 64 blocks (32 KB)
writes `screenChanged {was, now, blockSize, at}`, logs "Screen changed outside the app: ..." once in device.log, and `app_state`
returns `screenChanged {wasFree, nowFree, at}` (bytes). A store whose final check failed drops the baseline (no false alarm; the next
check starts over). Not run while live holds the screen (that path never queries the screen).
Code: `src/core/outside.rs`; hooks in service.rs (device_check, send_version, app_state, settings_update `screenChanged: "accept"`),
settings.rs sanitize (both keys written only when set), device_service.rs (fake `free` + `fake_set_free` test hook), app.js banner.
Test: `a_check_flags_screen_content_changed_outside_the_app` (fake device: first check, wobble inside tolerance, big change, repeat
keeps "was", accept, rebase after a store, failed final check). Full suite passes at default threads.

PM to verify on hardware: (1) after a real store, check twice: no banner (is `i_block_free` stable between reads, and across a
restart? if it wobbles by more than 64 blocks, raise TOLERANCE_BLOCKS in outside.rs); (2) the banner would only be seen after
another program writes to the screen, so a cheap proof is to read `screenBaseline` in settings.json against the value `cs2` info
reports. Not verified: any of this on the real screen; the banner look in the app (reuses the existing banner classes).

## C3: preview on the real screen (My themes and Browse)

User request 2026-10-19 (after 4.7.1). What changed:
- **My themes:** selecting a theme card shows it on the real screen at once (the theme as it is now: picture + live layer, streamed
  even when it would not need streaming). Selecting another swaps the picture in the same stream (no reconnect; the page
  debounces 150 ms so rapid clicking sends only the last one). The selection bar says "Previewing on the screen"; a ghost
  "Preview" button appears when the selected theme is not being previewed (after the idle end, or a selection made elsewhere).
- **Browse:** a click on a card (not on its buttons) selects it and previews its **thumbnail picture**, full screen, as a still
  (cover fit). Online thumbnails are fetched once over https (max 6 MB) into `<app folder>\preview\`, cached for a day; local
  thumbs (Wallpaper Engine / Lively) are read directly. Items without a thumbnail (e.g. scenes with none) say "This item has no
  picture to preview." in a toast. Videos/scenes are NOT played or recorded for a preview (that would need recording first); only
  their picture is shown. A bar at the bottom shows the title, "Previewing on the screen" and Stop. Previewing never adds anything.
- **Leaving ends it:** going to another view (On screen, Settings opens a drawer and does not leave My themes: preview stays until
  the user leaves the view), clearing the selection, "Use this theme", closing the window (the close handler ends it), the page
  closing, 2 minutes with no pointer/keyboard activity ("Preview ended." toast), and a backend safety timer: a preview the page
  has not refreshed (30 s keepalive) for 150 s ends by itself, so it can never keep running unseen. Tray Quit stops everything.
- **Live off:** a temporary stream starts (like Screen fit tuning); ending it uses the normal stop, which is an instant
  switch back to Embedded when the previewed picture is not the Embedded one (the preview theme is marked `not_embedded`) and the
  usual fade when it is. The Live setting is never touched (checked). **Live on:** the running stream is given the preview
  theme and gets the live theme back afterwards (same pipeline, no reconnect).
- **Use this theme:** sets it as the live theme (as before), ends the preview, goes to On screen. With Live off the toast says
  "Theme: “X”. Store it as Embedded here when you are happy." The "Store as Embedded" / "Update Embedded" button and "Use and
  store as Embedded" are gone from My themes (the On screen editor keeps "Embedded: X · Store this as Embedded").
- **Nothing is saved by a preview:** no settings.json, no theme.json, no stale mark, no live-theme change (tested: files byte-identical,
  `baseStale` false). A device task (upload/check) pauses a preview like live and it carries on afterwards (tested).
- Code: `live_host.rs` (preview_start / preview_end / preview_keepalive, watcher, `status.previewing`), `core/preview_screen.rs`,
  commands `screen_preview` / `screen_preview_end`, `public/js/screenpreview.js`, hooks in `public/app.js`
  (`SP`, setView, theme card, renderSelBar, Browse card + bar). Window close hook in `live_app.rs`.
- Verified: unit tests (host with Live off/on, swap without reconnect, live theme change during a preview, device task pause,
  forgotten preview timeout, stop forgets; App-level "saves nothing"; picture preview fills the canvas); full suite; a quiet DEBUG
  fake-device instance driven through the real page (`tools/ui-shots/preview-flow.mjs`: 14 checks incl. rapid clicks, Use this
  theme, Live on/off) with no page errors; screenshot of the selection bar. Not verified: on the real screen (first frame time,
  instant switch back), Browse in the running app (no sources enabled in my scratch home; only the backend and the picture
  renderer are tested), the window-close and idle-timeout paths in a real window, and the 2-minute page timer.

## C4: `CoolerScreen.exe --quit` (4.9.1)

What it is: a clean way for the installer workflow to quit the running app (tools/README.md has the exit codes).
`--quit` is handled at the very top of `main()` (before Tauri or the single-instance plugin start), so it can return its own exit
code, never creates a window and never starts an app. Exit codes: 0 quit, 1 asked but still running after 20 s, 2 refused (a visible
job is queued or running: upload, conversion, store, recording; nothing done), 3 no running instance.

How: the running app owns a named event `Local\CoolerScreenQuit-<hash of its app folder>` (a thread blocked on it: no polling, nothing
runs until signalled). Because the name follows the app folder, an instance with another COOLERSCREEN_HOME (every test instance)
can never be reached by, or answer for, the installed app. `--quit` signals it and reads `quit.result` ("ok <pid>" or "busy") in
the app folder, then waits for that pid to end. The app then runs the existing `quit_app` (same as tray Quit: `live.stop()`
hand-back, exit watchdog 3 s). device.log gets "quit requested (--quit): the tray Quit path" or "...a job is running: refused".

**PM install recipe:**
1. `& CoolerScreen.exe --quit` (the installed exe, normal app folder); `$LASTEXITCODE`: 0 = quit, go on; 3 = not running, go on;
   2 = a job is running: wait and retry (do not force); 1 = still running after 20 s: look before forcing.
2. Run the installer silently (`/S`) and wait for it to end.
3. `CoolerScreen.exe --background` (quiet start).
(`Start-Process -Wait -PassThru` gives the code for a GUI-subsystem exe; plain `& exe` does not wait.)

Plain WM_CLOSE (taskkill without /F): not changed. With a window it already goes through the close handler (hides to the tray, or
destroys the window with Live on); with no window there is nothing to receive it, and `taskkill` reports it could not close the
process. That is why `--quit` exists; I did not add a hidden helper window just for it.

Verified with quiet DEBUG instances under a scratch COOLERSCREEN_HOME, fake device (script in my scratchpad `quittest.ps1`):
1. no instance: exit 3. 2. while a store job ran: exit 2, the app kept running and the job finished. 3. when idle: exit 0 after
1.0 s, the process was gone and device.log shows "quit requested (--quit): the tray Quit path" then "live: stop". 4. again: 3. The
user's installed app was not touched by `--quit` (different folder, different event).
Not verified: against a release build (by design, never against the user's), the 20 s "still running" path, a real USB stop.

**My mistake to know about:** my first test launch of a debug instance forgot `COOLERSCREEN_MULTI=1`, so the single-instance
plugin forwarded that launch to the user's running 4.9.0 (pid 7356) and its callback (`show_main`) probably brought its window up
once (around 14:17-14:18 local). I did not touch the app otherwise; the test instances now always set MULTI. Worth knowing for
the user's fullscreen use: any debug instance launched without MULTI forwards to the installed app. (`--quit` itself never
starts Tauri, so it can not forward.)
